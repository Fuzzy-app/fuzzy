# 構成とデータフロー

## 全体構成

```text
和歌山大学Moodle
	↓ Content Script
ブラウザ拡張機能 Background Service Worker
	↓ Native Messaging protocol v0
FuzzyNativeHost.exe
	↓
engine-core
	├── SQLite v0（正本）
	├── 全文検索索引（再生成可能）
	└── 利用者が選んだ資料フォルダー

Fuzzy.exe
	├── 初期セットアップ
	├── Native Messaging登録・修復
	├── 保存先再スキャン・索引再構築
	└── バックアップ・起動時復旧

GitHub Pages
	├── 製品概要
	├── 導入手順
	├── プライバシーポリシー
	├── GitHub Releaseへの導線
	└── Chrome Web Store／Edge Add-onsへの導線
```

## コンポーネント

### `apps/extension`

- WXT、Svelte、TypeScript
- Manifest V3
- Moodle上のContent Script UI
- Popup
- Background Service Worker
- 保存先候補、資料保存、ZIP提案
- ダッシュボード、締切、検索
- ルール、違反、重複候補
- 通知、ICS出力
- IndexedDB表示キャッシュ

Content ScriptはNative Messagingへ直接接続せず、Backgroundへ中継します。

### `apps/native-host`

- Rust
- Chrome系Native Messagingの4byte little-endian長プレフィックス
- API envelopeの検証
- すべてのコマンドのengine-coreへの振り分け
- 大容量資料の分割転送セッション
- 標準出力へログを混ぜない

### `crates/engine-core`

- SQLite v0
- 保存ルートとパス検証
- ファイル保存とZIP展開
- 再帰走査
- PDF／DOCXテキスト抽出
- Tantivy全文検索
- BLAKE3完全一致
- SimHash／LSH類似候補
- ルール照合
- 課題、通知、同期履歴
- バックアップ、復元、欠損管理

desktopとnative-hostが同じロジックを共有します。

### `apps/desktop`

- Tauri 2、SvelteKit
- Windows 11用NSIS
- 初期セットアップ
- native-host同梱
- Chrome、Chromium、Edgeのユーザー単位登録
- 拡張機能の実応答による導入確認
- 保存先の再スキャン・変更
- バックアップ・復元
- DB・索引破損時のGUI復旧

### `packages/shared`

- TypeScript共有型
- Fuzzy API interface
- Native Messaging client
- Background API
- ts-rsでRustから生成したwire DTO
- 開発・テストで明示使用するsample data

本番APIはnative-hostだけを利用し、接続失敗時にsample dataへ暗黙に切り替えません。

### `apps/site`

- Vite静的サイト
- GitHub Pagesへdeploy
- 概要、導入、プライバシー、公開導線
- 利用データを受信するサーバー機能なし

## データの正本

| データ | 保存先 | 位置づけ |
|---|---|---|
| コース、課題、ルール、通知、保存済み資料メタデータ | SQLite | 唯一の正本 |
| 全文検索 | Tantivy索引 | SQLiteと資料から再生成可能 |
| ダッシュボードキャッシュ | IndexedDB | 表示専用、正本ではない |
| 資料本体 | 利用者が選択したフォルダー | 利用者管理 |
| バックアップ | OSダイアログで利用者が選択 | SQLiteの明示コピー |

 SQLiteは通常`%LOCALAPPDATA%\Fuzzy\fuzzy.db`です。旧`%APPDATA%`側のDBは移行せず参照しません。旧世代のSQLiteはデータを変更せず退避し、利用者確認後に初期化画面から新規作成します。アンインストール時はFuzzyが管理するSQLite・検索索引・表示キャッシュを削除しますが、利用者が選択した資料フォルダーとバックアップは削除しません。

## Moodle資料取得

1. Content Scriptが対応Moodle画面から資料候補を収集する
2. 利用者が保存対象と保存先を確認する
3. Backgroundが送信元と資料URLの同一オリジンを検証する
4. ブラウザの既存ログイン状態を使って資料を取得する
5. Cookie、Authorization header、認証情報をpayloadへ含めない
6. 取得済みバイトだけを小さなBase64チャンクへ分割する
7. Native Messagingの同一接続でnative-hostへ送る
8. native-hostがサイズ、MIME、パス、名前、保存ルートを再検証する
9. 保存成功分だけをSQLiteと索引へ登録する

制限:

- 1ファイル64MiB
- 保存1転送128MiB
- 最大20ファイル
- Base64文字列192KiB以下のチャンク
- native-host復号後256KiB以下

## セキュリティ境界

- 対応MoodleのHTTPSオリジンだけへhost permissionを付与
- リダイレクト後も同一オリジンを要求
- Native Messagingの`allowed_origins`を正式なFuzzy IDだけへ限定
- request ID、command、payload、サイズを境界で再検証
- 保存ルート外、相対移動、Windows予約名、reparse pointを拒否
- 既存ファイルを上書きしない
- ZIP Slipと展開上限を防止
- HTML偽装や無効DOCXを拒否
- DB詳細や絶対パスを拡張機能エラーへ公開しない
- 外部解析、広告、テレメトリを行わない

## 利用者操作が必要な境界

次は自動実行しません。

- ブラウザ拡張機能の追加
- 資料保存
- ZIP展開
- 保存先変更
- 再スキャン・索引再構築
- バックアップ書き出し・復元
- 破損DB保全後の新規開始
- 資料やバックアップの削除

インストーラーはnative-hostの配置・登録・解除を自動化しますが、拡張機能の権限承認とデータに影響する操作は利用者の明示操作を要求します。

## 公開時に確認する接点

- manifestのIDとNative Messaging許可元
- `NativeApiClient`のhost名とdesktop配布設定
- protocol version
- Rust wire DTOと生成TypeScript
- SQLiteスキーマとAPI契約
- ストア権限申告とプライバシーポリシー
- Windows署名主体と公開ページの公開者名
- GitHub Release versionと全package/crate version
