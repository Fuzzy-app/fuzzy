# 公開ロードマップ

## 結論

Fuzzyは技術的に一般公開可能ですが、ローカルで生成した未署名成果物をそのまま正式版として公開しません。公開可否は、コードの完成だけでなく、公開主体、ストアID、審査環境、コード署名、クリーン環境QAが揃った時点で判断します。

現在の対応範囲はWindows 11と`https://*.wakayama-u.ac.jp/*`のMoodleです。ストア上でPublicにしても、対応Moodleへログインできない利用者は主要機能を利用できません。公開ページとストア説明で対象を明示します。

## 公開前に確定するもの

- [ ] 公開主体を個人、チーム、大学公式のいずれにするか決定した
- [ ] コード署名とストアに表示する公開者名を統一した
- [ ] サポート用メールアドレスを用意した
- [ ] 大学およびMoodleとの関係を正確に説明できる
- [ ] 大学公式でない場合は、公式製品と誤認させない表示を用意した
- [ ] `com.fuzzy.desktop`と`jp.ac.wakayama_u.fuzzy.native_host`を公開主体に合わせて維持または変更すると決定した
- [ ] 審査専用Moodleアカウントまたは審査可能なデモ環境を用意した

公開主体が管理しない名前空間を使っている場合は、初回リリース前に識別子を変更します。公開後の変更はNative Messaging登録、バックアップ、更新導線へ影響するため、初版で固定します。

## フェーズ1: mainの安定化と公開サイト

1. 機能統合PRをレビューし、必須CIが成功していることを確認する
2. mainへマージする
3. GitHub PagesのSourceを`GitHub Actions`にする
4. `Deploy Fuzzy site to GitHub Pages`をmainで実行する
5. トップページとプライバシーポリシーがHTTPSで閲覧できることを確認する
6. ダウンロード先とストアURLが未確定の間は「公開予定」のまま無効化する

具体的な操作は[GitHub Pages運用](GitHub-Pages運用.md)を参照します。

## フェーズ2: ストアIDの予約

1. Chrome Web Storeの開発者アカウントを用意する
2. 拡張機能ZIPを未公開アイテムとしてアップロードする
3. Chrome Web Storeが割り当てたItem IDと公開鍵を取得する
4. Microsoft Edge Partner Centerにもドラフトを作成し、Edge側IDを取得する
5. 正式IDを`apps/desktop/distribution.config.json`の`extensionIds`へ追加する
6. Chromeの公開鍵とIDを`apps/extension/wxt.config.ts`へ反映する
7. `extensionStoreUrl`へ、許可したIDで終わる実在するHTTPS詳細URLを設定する
8. Chrome／Edge双方のIDがNative Messaging manifestの`allowed_origins`へ出力されることを検証する

現在のQA用IDを、ストアの正式IDと仮定して公開してはいけません。詳細は[ブラウザストア申請](ブラウザストア申請.md)を参照します。

## フェーズ3: Windows署名と審査用配布

1. コード署名方法を決定する
2. 同じ公開者IDで`Fuzzy.exe`、`FuzzyNativeHost.exe`、`Fuzzy-Setup.exe`へ署名する
3. 署名後のファイルを変更していないことを検証する
4. ストア審査担当者が取得できる審査用インストーラーを用意する
5. 審査用インストーラーのバージョンと提出ZIPのバージョンを一致させる

詳細は[Windows配布とコード署名](Windows配布とコード署名.md)を参照します。

## フェーズ4: 限定公開QA

Chrome Web Storeでは、最初からPublicにせずPrivateまたはUnlistedで実利用テストを行います。公開範囲にかかわらずポリシー審査は必要です。

1. ChromeとEdgeの審査へ提出する
2. 審査担当者向け手順と専用Moodle認証情報を非公開欄へ記載する
3. 承認後、信頼できるテスターで導入・更新・削除を確認する
4. [リリース前QA](リリース前QA.md)の全必須項目を完了する
5. 重大な不具合があれば公開せず、別ブランチとPRで修正する

## フェーズ5: v0.1.0正式公開

1. ストア審査を承認後の手動公開に設定する
2. mainの対象コミットへ`v0.1.0`タグを付ける
3. GitHub Releaseを作成する
4. 署名済み`Fuzzy-Setup.exe`、`SHA256SUMS.txt`、リリースノートを添付する
5. 公開ページへバージョン、公開日、対応環境、既知の制限を掲載する
6. 公開ページのWindows導線をGitHub Releaseへ接続する
7. 公開ページとデスクトップの拡張機能導線を正式ストアURLへ接続する
8. Chrome／Edgeの公開を実行する
9. 公開ページから新規ユーザーとして導入できることを再確認する

## Go/No-Go判定

次のどれか1つでも満たさない場合はNo-Goです。

- [ ] mainの必須CIがすべて成功
- [ ] GitHub Pagesとプライバシーポリシーが公開済み
- [ ] GitHub ReleaseのダウンロードURLが実在
- [ ] すべてのWindows配布バイナリが有効な署名を持つ
- [ ] ストアの正式IDとNative Messaging許可元が一致
- [ ] ストア掲載内容と実際の権限・処理データが一致
- [ ] 審査用Moodle環境で主要機能を再現可能
- [ ] クリーン環境QAが完了
- [ ] 一般利用者へターミナル、レジストリ編集、ZIP展開を要求しない
- [ ] 保存済み資料の自動移動・自動削除を行わない

## 公開後

- バグ修正はmainから`issue<番号>`ブランチを作り、PRとCIを経由する
- 拡張機能、native-host、デスクトップ、Native Messaging契約の互換性を同時に確認する
- ストア更新はmanifestのバージョンを必ず増加させる
- Windows更新でも同じコード署名主体を使用する
- プライバシー、権限、対応サイトに変更がある場合は、コード公開前にストア申告と公開ページを更新する
- セキュリティ事故や重大なデータ破損が疑われる場合は、新規配布を停止し、既存Releaseとストア公開状態を確認する
