# 開発判断・継続時の前提

最終更新: 2026-07-29

この文書は、仕様書・Issue・実装の間で判断が必要になった際に、チームとAIが共有する合意事項を残す。機能の正規仕様は `仕様書.md`、個別タスクの完了条件はGitHub Issueを参照する。

## 判断の優先順位

1. 実装の着手・完了判定はGitHub Issueの記述を優先する。
2. Issueと `docs/仕様書.md`、API契約、DB設計の間に相違を見つけた場合、実装者は相違点を報告する。黙って仕様を上書きしない。
3. 型・API・DBスキーマを変更する場合は、従来どおり `packages/shared/src/types.ts`、`docs/api/contract.md`、`crates/engine-core/fixtures/schema.sql` の整合を確認する。

## 担当とレビュー

- subaruは主にバックエンドと全体コードレビューを担当する。
- 拡張機能とnative-hostの接点を変える際は、担当をまたぐためPRで明示して相談する。

## Moodle資料の取得と保存

- 対象は和歌山大学のMoodleである。年度によりページ構造が変わることを前提に、特定年度の固定DOMだけに依存しない解析を目指す。
- 認証が必要なMoodle資料は、ログイン済みブラウザ拡張機能が取得する。native-hostがブラウザの認証情報を保持・再利用して取得する設計にはしない。
- 取得済み資料をnative-hostへ渡して保存処理を行う。Issue #107で、Cookie等を含めないBase64チャンクを同一Native Messaging接続内で順次送る方式に決定した。保存前の類似照合も専用の`beginCheckSimilarFile`→`appendCheckSimilarFileChunk`→`checkSimilarFiles`で同じ分割方式を使い、単一メッセージへファイル全体を含めない。この破壊的変更に合わせ、Native Messaging契約バージョンを`2`へ更新する。拡張機能側は192KiB文字単位で分割し、native-hostは復号後256KiB以下のチャンク、1ファイル64MiB、保存転送は合計128MiB・20ファイルまでを受理する。転送中データはプロセスメモリに保持し、上限を超える要求は処理前に拒否する。類似照合はbackgroundで全タブ合計2件まで、保存パネルでも2 workerまでの並列実行とし、失敗時も実行中workerの収束を待って、複数のnative-hostプロセスが同時に大容量データを保持することを避ける。
- ユーザーが保存対象と保存先を確認し、保存操作を行った後は、必要な保存先フォルダを自動作成してよい。保存済みファイルの自動移動・自動削除は引き続き禁止する。

## PR #93 / Issue #91 のスコープ判断

- Moodle再ログイン補助は単独のクリック自動化ではなく、ログイン前後の保存パネル状態、明示ログアウト後の抑止、ページ起動判定までを一つの利用者フローとして扱う。この範囲の変更はIssue #91の受け入れ対象とする。
- 同じPRに含まれるルール整合性画面、API・型・DBスキーマの整合、保存パネルの狭幅表示・開閉ハンドル改善は、PR #93でまとめてレビュー・受け入れる判断とする。以後同規模の複数機能を扱う場合は、PR本文にIssueごとの変更一覧、仕様・型・API・DBへの影響、個別のテスト結果を記載する。
- 認証補助の実装責務は、ページ判定（URL・DOM）、ログアウト抑止状態（sessionStorage・browser.storage.local）、操作調停（クリック・遷移）、UI起動判定へ分ける。一つのモジュールへDOM判定・永続化・UI起動を集約しない。
- Moodle未ログインページでは再ログイン対象と判定した画面以外の処理を起動しない。Moodle障害時のキャッシュ表示境界は `仕様書.md` 3.5を正とする。

## 外部連携

- データは原則ローカル完結とする。
- Googleカレンダー／Google Tasksへの直接追加は、ユーザーが認証し、送信対象を確認して明示的に許可した場合に限る例外とする。許可なしでは外部送信を行わず、Google認証の解除と連携停止を可能にする。
- Fuzzy独自のスマートフォン向けプッシュ通知は実装せず、スマートフォンでの通知はユーザーが許可したGoogle連携先に委ねる。
- 将来はWindows通知センターとのデスクトップ通知連携を追加する。常駐方式と、ブラウザ通知との重複防止は専用Issueで決定する。
- 発表時点では全機能の完成を目標とする。ただしGoogle連携は優先度を下げ、まずローカル機能とICS出力を完成させる。

## データ移行と型生成

- Issue #45で、エクスポート／インポート形式は専用アーカイブではなく生SQLiteファイルに決定した。書き出しにはSQLite Online Backup APIを使い、Tantivy索引は同梱しない。インポート後は`search_index_meta`と移行先の索引を無効化し、再スキャンで再構築する。
- RustのAPI DTOを正とする型は`ts-rs`で`packages/shared/src/generated/`へ生成する。生成物は手編集せず、`bun run generate:types`で更新する。Rust DTOがまだ存在しない型だけを`packages/shared/src/types.ts`に手書きで残す。

## Issue #115 初期／再セットアップと整理ルール

- `save_initial_setup`は未設定状態の初回確定専用とし、設定済みの再セットアップへ流用しない。初回保存は保存ルートを新規設定できる一方、登録済み`files.saved_path`の付け替えを前提としていないため、設定済みDBへ再実行すると保存ルートと登録済みパスの整合を壊し得る。
- 設定済み画面は`get_saved_setup_configuration`でSQLiteの現在値を読み込み、利用者が変更点を確認した後だけ`save_setup_changes`を呼ぶ。初回向けの拡張機能導入手順と、設定済みの変更・保守導線を同じ完了フローへ混在させない。
- 再セットアップの競合検知には、クライアントが解析・生成しないopaqueな`revision`を使用する。保存日時だけでは拡張機能側からのルール更新を検出できないため、revisionは保存ルート、推定結果、グローバルルール、初期セットアップ管理のコース別選択を含む保存済み投影から導出する。照合不一致時は何も書き込まず、最新値の再読込と利用者による再確認を求める。
- 保存先変更では、旧保存ルート配下のSQLite内パス情報だけを同じ相対パスで新保存ルートへ付け替え、実体未確認・未索引へ戻す。保存ルート、ルール、推定結果、初期セットアップ管理の選択、SQLite内パス情報は1つのトランザクションで確定する。保存済み資料の実ファイルは移動・削除・改名せず、新保存先に自動作成もしない。
- 初期セットアップ、再セットアップ、拡張機能の常設ルール管理は、年度、学期、科目、課題、授業回、固定フォルダー名からなる共有の構造化ルールモデルを使用する。内部テンプレートへの変換はAPI境界へ閉じ込め、内部トークンを利用者向けUIへ表示しない。既存形式を損失なく変換できない場合は黙って正規化せず、現在値を保持して明示選択を求める。
- 長時間処理は同じ表示領域で実行中から成功、警告付き完了、失敗へ遷移させる。Tauriの進捗通知とコマンド結果で終端状態を一致させ、終端通知を1回だけ返す。処理中の二重実行を防ぎ、中止できない処理はその旨を示し、失敗後だけ安全に再試行できるようにする。

## Issue #59 本番統合と配布

- 本番画面のAPI接続は拡張機能backgroundへ集約し、content scriptからnative-hostへ直接接続しない。接続できない場合はサンプルデータへ切り替えず`NO_NATIVE_HOST`を表示する。ダッシュボードだけは過去にnative-hostから取得した実データのローカルキャッシュを明示して表示できる。初回失敗を固定せず、対象Moodleタブがある間だけ再接続できるようにする。
- Moodle課題同期はcourse-module由来の安定IDを必須とするコース単位の完全スナップショットに決定した。部分セクション、安定IDを欠く活動を含む画面、個別活動ページからは同期しない。現在のNative Messaging契約バージョンは、検索結果の詳細表示と明示的な資料オープン操作を含む`6`とする。
- IndexedDB表示キャッシュは拡張機能originのbackgroundで更新する。content scriptのWeb Storage／IndexedDBはMoodleページoriginに属するため正本・表示キャッシュの保存先として使用しない。
- Windows配布はNSISインストーラーを標準とし、native-hostの同梱、ユーザー単位のNative Messaging登録、修復、アンインストール時の登録解除を自動化する。一般利用者へコマンド操作を要求しない。ブラウザ拡張機能の追加は権限確認が必要なため、同梱版または公式ストア上で利用者が明示的に行う。
- ローカルテスト成果物は未署名で作成できるが、一般公開版は外部のWindowsコード署名証明書を設定してから配布する。
- DBを開く前には`app_settings`を参照できないため、Windowsの本番DBは`%LOCALAPPDATA%\Fuzzy\fuzzy.db`を既定とし、開発・テスト時だけ`FUZZY_DB_PATH`で上書きする。旧版の`%APPDATA%\Fuzzy\fuzzy.db`は移行せず参照しない。旧世代のSQLiteは初期化画面から新規作成する。
- 今回が初回リリース前のため、完成形SQLiteスキーマを`user_version = 2`とし、開発途中のマイグレーションは同梱しない。既存DB・インポート元は`app_settings`など一部の存在だけでFuzzy DBと判定せず、v2の全必須テーブル・列・制約・索引・外部キー整合性を検証する。不完全・別世代・世代不明のDBは変更せず明示的に拒否し、デスクトップの利用者確認後に内部データを退避して初期状態へ戻す。
- 課題詳細HTMLはログイン済み拡張機能だけが同一オリジンで取得する。Cookie・認証情報・課題本文をnative-hostや外部へ渡さず、SQLiteには正規化済み詳細URLと3値の提出可否だけを保存する。期限切れ、提出済み、`submission_mode`から提出不可を推測しない。
- 初期設定確定後と利用者が復旧画面から明示したときは、保存ルートを再走査して既存資料をSQLiteへ冪等登録し、全文索引・ルール適合注釈・重複候補を再計算する。DBにあるが実体を確認できない資料は自動削除せず、個別の読み取り失敗も警告に留める。
- 初期走査でフォルダ名から得たコースは`local-scan:`接頭辞の安定IDで保持し、後から同名のMoodleコースが一意に判明した場合だけ実Moodle IDへ昇格する。これにより既存資料の`course_id`を維持し、同名候補が複数なら黙って統合しない。
- バックアップ／復元、再スキャン、検索索引再構築はTauriの復旧画面から実行できるようにし、一般利用者へコマンド操作を要求しない。処理はファイルの移動・削除を行わず、インポート後はGUI処理内で索引を再構築する。
- 再スキャンで登録済みパスの実体が見つからない場合は、履歴保全と自動削除禁止を両立するため`files.missing_at`へ記録する。欠損中は通常の集計・検索・違反・重複候補から除外し、同じパスへの再出現時に解除する。
