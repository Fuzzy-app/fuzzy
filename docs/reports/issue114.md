# issue #114 実装・計測結果

計測日: 2026-07-28
環境: Windows 11、Rust debug test build、SQLite in-memory

## 実装した改善

- 相対パスの全親階層を年度・学期・科目・授業回へ役割分類
- `1年前期`、`2年後期`、`1Q`〜`4Q`、`Nクォーター`を学期として認識
- 未分類セグメントが複数ある場合は科目を自動決定せず、明示確認候補を返す
- 候補へ評価可能件数、科目位置、ファイル名規則、候補固有の代表例を保持
- パス・サイズ・更新日時が一致する再走査でBLAKE3／SimHashを再利用
- 前回観測値をSQLiteから1回で一括取得し、ファイル件数分の個別SELECTを廃止
- 再ハッシュが必要なファイルだけをCPU数に応じて最大4並列で処理
- メタデータ変更がない再走査ではルール・重複グループの全件再計算を省略
- Moodleコース表示時は対象コースだけを探索し、同時要求と5分以内の再要求をまとめる
- コース解決を相対コース文脈単位でキャッシュ
- SQLiteファイル登録を256件単位のtransactionへまとめ、バッチ失敗時だけ単件再試行
- 本文抽出を最大4並列、Tantivyへの反映を64ファイル単位の1コミットへまとめる
- `files.saved_path`の照合順序をクエリと同じ`NOCASE`へ統一し、区切り文字・Windows verbatim prefixも登録前に正規化
- 開発環境、依存パッケージ、VCS、キャッシュ、構造から判定できるビルド生成物を再帰探索しない
- 除外外のソース・設定・バイナリはハッシュ登録し、本文抽出非対応形式を失敗件数へ含めない
- 走査・登録・索引・最終処理と終端状態をTauriイベントへ通知し、画面には内部フェーズ名を出さず全体進捗として表示
- PDF検索結果へ索引作成時の総ページ数を付け、検索ヒットのページが`1..pageCount`外なら返さない

## 実利用データで判明した主因

初期保存が5分以上続いた環境では、走査済みSQLiteに32,567ファイル、約3.32GiBが登録されていた。主な増加要因は複数のPython仮想環境で、`.venv/Lib`だけで20,306ファイルを占めていた。旧実装はこれらもハッシュ化し、本文抽出対象はTantivyへ1ファイルごとにcommitしていたため、停止しているように見える長時間処理になっていた。

同じファイル一覧へ今回の組み込み除外名を適用すると、30,341ファイルを探索前に除外し、処理対象は2,226ファイルになる。ファイル数では約93%減る。除外外の`.py`、`.json`、`.ipynb`、設定ファイル、実行ファイルは残し、本文抽出非対応のバイナリもBLAKE3／SimHashとメタデータの登録だけを行う。

全文索引候補が1,534件の場合、Tantivyのcommit回数は従来の最大1,534回から、64件単位の最大24回へ減る。

## PDFページ番号

実データ上位のPDFを別実装でも照合したところ、総ページ数660、391、376、330、289等はPDFページツリーと一致していた。一方、画面の`153ページ`は総ページ数ではなく検索語が一致したページ番号であり、総ページ数を併記していなかったため意味を判別できなかった。

検索APIへ`pageCount`を追加し、画面では`153 / 660ページ`のように表示する。また、再索引前の古いヒット等でページ番号が総ページ数を超えた場合はページ情報なしとして扱う。ページ数の取得方式や索引処理の内部フェーズ名は利用者向け画面へ表示しない。

修正前の`files.saved_path`はBINARY一意索引、upsertは`COLLATE NOCASE`検索だったため索引を利用できず、同じテストは4分の上限内に完了しなかった。さらに、同じWindowsパスでも`\\?\`接頭辞や区切り文字が異なると別行を作れた。修正後は`EXPLAIN QUERY PLAN`と回帰テストでcase-insensitive一意索引の利用・パス正規化・既存行の再利用を確認した。

この生成テストはファイル内容抽出やTantivy投入ではなく、#114で問題になった階層推定とSQLite登録経路を分離計測する。実資料の抽出時間はファイル形式・サイズ・ディスク性能に依存するため、backendは進捗イベントを通知するが、利用者向け画面では内部処理名を隠して全体の件数と割合だけを表示する。
